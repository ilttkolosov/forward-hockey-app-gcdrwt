# Повторный аудит iOS-лога мессенджера

Дата анализа: 21.08.2026

Исходный файл: `Без названия 4.rtf`

Проверяемая ветка: `stabilization/ios-messenger-request-performance`

## Резюме

Сильная задержка первых 10–15 секунд не была вызвана миграцией или индексацией
SQLite. Локальные справочники и окна сообщений открывались быстро. Главная
причина — одновременный запуск большого числа необязательных сетевых и нативных
операций сразу после cold start и во время первых навигационных переходов.

Особенно заметны два участка:

1. Общий запуск удерживал интерфейс 4 965 мс, хотя локальные справочники были
   готовы за 19 мс, а игроки — за 8 мс.
2. Первое открытие мессенджера совпало с ожиданием `/rules/status` 5 967 мс и
   `/chat/rooms` 7 460 мс. При этом в SQLite уже находились 12 комнат.

После завершения этого пакета операций локальная отрисовка действительно
стабилизировалась, что совпадает с наблюдением пользователя.

- 1 запрос `/rules/status`;
- 2 проверки push preference и 1 push registration;
- остальные запросы относятся к открытию комнат, синхронизации, отправке и
  прочтению сообщений.

## Производительность ленты сообщений

Шесть открытий комнат дали следующие локальные показатели:

- нажатие → фокус экрана: 57–73 мс;
- получение первого окна SQLite: 7–14 мс;
- первоначальное позиционирование: 147–315 мс.

Это подтверждает, что основная модель local-first работает. Серверная
синхронизация завершалась позднее и не была необходима для первого кадра.

Один раз React Native сообщил:

`VirtualizedList: You have a large list that is slow to update`, `dt=1176 ms`.

Предупреждение возникло при добавлении сообщения. Строки сообщений уже
изолированы через `React.memo`, поэтому единичный замер сам по себе не доказывает
постоянный дефект ленты. Его необходимо повторно проверить без стартовой
конкуренции. Если предупреждение сохранится, следующий этап — Instruments Time
Profiler/React Profiler на конкретном чате с медиа.

## Системные и сторонние предупреждения

- AppMetrica 6.6.0 активировалась, но сообщила о некорректном
  `appBuildNumber`. В конфигурацию добавлена явная передача числового номера
  нативной сборки.
- 49 строк `Reporter disconnected` относятся к системному/нативному reporter и
  появились сериями после XPC/audio/haptic interruption. Фатального падения
  приложения в этом фрагменте нет.
- Четыре `Result accumulator timeout: 3.000000` и ошибки CoreHaptics/AudioSession
  совпали с перегруженным первым периодом. Это не HTTP-ошибки сервера.
- Конфликт ограничений `TUIKeyboardContentView` относится к системной клавиатуре
  iOS. Он появился при остановке debug session, а не при первом открытии чата.
- StoreKit sandbox и предупреждение `UIScene` не объясняют задержку мессенджера.

Лог не содержит полноценной выборки Main Thread/FPS, поэтому точное количество
пропущенных кадров по нему определить нельзя. Вывод о рывках основан на
измеренных задержках, системных timeout и предупреждении VirtualizedList.

## Реализованные изменения

### Повторные запуски

- Локальная/bundled startup-конфигурация применяется сразу, без ожидания
  NetInfo и HTTP.
- Предстоящие игры, тренировки, исторические матчи, push, AppMetrica и другие
  необязательные задачи больше не участвуют в критическом пути запуска.
- Фоновые задачи запускаются после первого интерактивного кадра, после
  завершения навигационных анимаций и с интервалами, а не одним пакетом.
- Проверка серверной сессии и подключение realtime не конкурируют с cold-start
  интерфейсом.
- Проверка Правил начинается после завершения перехода в мессенджер.

### Первый вход после установки или новый профиль

Если для пользователя нет ни локального списка комнат, ни маркера успешной
подготовки, показывается отдельный экран «Подготовка мессенджера»:

- отображаются реальный этап, progress bar и значение 0–100%;
- список комнат загружается и сохраняется в SQLite;
- после успешной подготовки записывается маркер версии bootstrap для данного
  пользователя;
- при ошибке остаётся понятный экран с кнопкой «Повторить»;
- после успешной подготовки этот экран больше не показывается при обычных
  перезапусках;
- существующим пользователям с заполненным SQLite маркер создаётся бесшумно.

### Фоновая синхронизация мессенджера

- первый фоновый room sync отложен на 15 секунд;
- прогрев истории отложен на 20 секунд;
- успешный room snapshot повторно используется фоновыми владельцами 60 секунд;
- псевдонимы синхронизируются не чаще одного раза в 5 минут;
- локальные комнаты отображаются до запуска удалённого refresh;
- удалённый refresh начинается только после завершения перехода к списку чатов.

## Ожидаемый результат следующего теста

На повторном запуске:

- главный интерфейс должен появляться после короткой локальной подготовки;
- страница «О программе» должна открываться без ожидания фоновой сети;
- список чатов должен сразу показываться из SQLite;
- сетевой refresh не должен останавливать или дробить анимацию перехода;
- экран 0–100% не должен появляться, если профиль уже подготовлен.

На чистой установке/новом профиле экран подготовки допустим один раз. После
достижения 100% последующие запуски должны идти по быстрому local-first пути.

Для контрольного замера желательно повторить: cold start → быстро открыть
«О программе» → вернуться → открыть «Общение» → открыть 2–3 комнаты → отправить
текстовое сообщение. Новый лог позволит отдельно подтвердить устранение
стартовой конкуренции и проверить единичное предупреждение VirtualizedList.
