# План реализации

## Правило выполнения

Каждый этап завершается работающим проверяемым состоянием, отдельным коммитом и публикацией в GitHub. Серверные секреты, production-токены, пароли и резервные копии в Git не попадают.

Основная мобильная ветка разработки: `feature/messenger-foundation`. Сервер создаётся в отдельном репозитории `forward-hockey-messenger-server`. Объединение с `main` выполняется только после успешной preview-проверки соответствующего пользовательского среза на iOS и Android.

## Этап 0. Контракт и архитектура

Результат:

- продуктовые границы;
- принятые решения;
- RBAC-матрица и шаблоны комнат;
- архитектура независимого сервера и БД;
- модель безопасности;
- черновой REST/WebSocket-контракт;
- порядок реализации.

Критерий завершения: документы согласованы и опубликованы в feature-ветке мобильного проекта.

## Этап 1. Серверный фундамент

1. Создать отдельный GitHub-репозиторий.
2. Инициализировать NestJS/TypeScript, PostgreSQL migrations, Redis и worker.
3. Подготовить Docker Compose для staging и production без секретов в репозитории.
4. Настроить Nginx, HTTPS, домен staging, health/readiness endpoints.
5. Добавить структурированные логи, CI, резервное копирование и инструкцию восстановления.

Критерий: чистый Linux-сервер разворачивает staging одной документированной процедурой; backup PostgreSQL успешно восстанавливается.

## Этап 2. Пользователи, роли и приглашения

1. Реализовать пользователей, профили, команды, сезоны и связи родитель–игрок.
2. Реализовать единый policy engine по [RBAC_MATRIX.md](RBAC_MATRIX.md).
3. Реализовать одноразовые приглашения, QR/deep link и ограничения полномочий создателя.
4. Реализовать access/refresh sessions, устройства, отзыв сессий и начального администратора.
5. Добавить табличные тесты ролей и попыток повышения прав.

Критерий: приглашённый пользователь получает ровно заданные роли, а запрещённые API-запросы и WebSocket-подписки отклоняются.

## Этап 3. Комнаты и группы

1. Создать шаблоны комнат из матрицы.
2. Автоматически пересчитывать членство при изменении ролей/сезона.
3. Реализовать read-only и write policies.
4. Реализовать архивирование комнаты и журналируемые исключения.

Критерий: все ячейки матрицы видимости/записи проходят серверные интеграционные тесты.

## Этап 4. Текстовый мессенджер

1. Добавить REST-историю, идемпотентную отправку и WebSocket-события.
2. Добавить SQLite-миграцию и отдельный messenger repository в приложении.
3. Реализовать список комнат, экран переписки, ответы, редактирование, удаление и unread state.
4. Реализовать outbox, повтор после сети и catch-up по курсору.
5. Добавить логи синхронизации без содержимого сообщений.

Критерий: сообщение не дублируется после обрыва сети, история и счётчики сходятся на двух устройствах.

## Этап 5. Push-уведомления

1. Связать Expo push token с пользователем и устройством.
2. Добавить категории мессенджера, deep links и настройки предпросмотра.
3. Обрабатывать Expo receipts и удалять недействительные токены.
4. Не менять существующие push матчей и локальные уведомления тренировок.

Критерий: уведомление доставляется и открывает правильную комнату на физическом iPhone и Android-устройстве.

## Этап 6. Фото, видео, реакции и аватары

1. Добавить безопасную временную загрузку.
2. Добавить проверку MIME/сигнатуры, лимитов и EXIF stripping.
3. Добавить миниатюры, обложки и при необходимости нормализацию видео.
4. Добавить реакции, просмотр медиа и кэш файлов приложения.

Критерий: неподдерживаемый файл не публикуется, закрытое вложение нельзя скачать без доступа к комнате.

## Этап 7. Администрирование и модерация

1. Пользователи, роли, команды, сезоны, блокировки и отзыв сессий.
2. Приглашения ссылкой и QR непосредственно из приложения.
3. Управление комнатами без автоматического чтения содержимого.
4. Жалобы, временные moderation grants и аудит.
5. Удаление учётной записи и экспорт/удаление по утверждённой политике.

Критерий: каждое чувствительное действие воспроизводится по аудиту, а скрытого универсального доступа к истории нет.

## Этап 8. Надёжность и безопасность

1. Нагрузочный тест до 500 WebSocket-соединений.
2. Тесты offline/outbox, повторной доставки, смены ролей и нескольких устройств.
3. Проверка rate limits, загрузок, утечек данных между комнатами и управления сессиями.
4. Проверка backup/restore PostgreSQL и object storage.
5. Обновление политики конфиденциальности и материалов магазинов.

Критерий: нет критических дефектов доступа/потери сообщений; восстановление подтверждено практическим тестом.

## Этап 9. Поэтапный запуск

1. Администратор и тренерский штаб.
2. Родительский комитет.
3. Пилот 10–20 пользователей на iOS/Android.
4. Все пользователи команды.
5. TestFlight и Google Play Internal Testing, затем выпуск версии ориентировочно `1.1.0`.

На каждом шаге проверяются доставка push, расход хранилища, ошибки синхронизации, жалобы и нагрузка. Возможность быстрого отключения entry point мессенджера управляется удалённой конфигурацией приложения.
