# Архитектура мессенджера

## Граница с существующей системой

Мессенджер не расширяет WordPress и не подключается к его базе данных.

```text
                         +-----------------------+
                         | WordPress / SportPress|
                         | матчи, команды,       |
                         | игроки, тренировки    |
                         +-----------+-----------+
                                     |
                                     | HTTPS REST
                                     v
+-------------+    HTTPS / WSS    +--+------------------+
| iOS/Android | <----------------> | Messenger backend  |
| Expo app    |                    | NestJS + Socket.IO |
+------+------+                    +--+--------+---------+
       |                                |        |
       | SQLite + SecureStore           |        +--> Redis
       |                                +----------> PostgreSQL
       |                                +----------> S3/MinIO + media worker
       |                                +----------> Expo Push Service
       +-----> WordPress API
```

Приложение объединяет данные только на уровне интерфейса. Отказ сайта не блокирует уже авторизованный мессенджер, а отказ мессенджера не блокирует матчи и расписание.

## Серверный контур

Предлагаемый отдельный репозиторий: `forward-hockey-messenger-server`.

Компоненты:

- Nginx — TLS, лимиты запросов и проксирование REST/WebSocket.
- NestJS/TypeScript — API, RBAC, бизнес-правила и фоновые задания.
- Socket.IO — события новых сообщений, реакций, статусов и изменения доступа.
- PostgreSQL — единственный постоянный источник истины.
- Redis — присутствие, краткоживущие блокировки, rate limit и масштабирование Socket.IO; сообщения в Redis не являются единственной копией.
- S3-совместимое хранилище или MinIO — оригиналы и производные медиа.
- Media worker/FFmpeg — проверка, миниатюры, обложки и нормализация видео.
- Expo Push Service — доставка в APNs и FCM по токенам устройств.
- Docker Compose — воспроизводимый запуск на Linux-сервере.

Целевой адрес API задаётся конфигурацией приложения, например `https://chat.hc-forward.com/api/v1`; WebSocket использует тот же origin.

## Владение данными

### PostgreSQL

Начальные сущности:

- `users`, `user_profiles`;
- `teams`, `seasons`, `team_memberships`;
- `guardian_player_links`;
- `roles`, `permissions`, `role_permissions`, `membership_roles`;
- `sessions`, `devices`;
- `invites`;
- `chat_rooms`, `chat_room_rules`, `chat_members`;
- `messages`, `message_attachments`, `message_reactions`, `message_receipts`;
- `reports`, `blocked_users`, `moderation_grants`;
- `audit_log`.

Все основные идентификаторы — UUID. Времена передаются и хранятся в UTC. Команда и сезон являются отдельными внешними ключами, а не строками в профиле.

### Redis

Redis хранит только восстанавливаемое состояние:

- активные socket-соединения и присутствие;
- распределённые rate limits;
- короткие блокировки обработки;
- очередь фоновых задач, для которой настроены повторы и dead-letter обработка;
- адаптер Socket.IO при нескольких экземплярах API.

### Медиа

В PostgreSQL находятся метаданные и состояние обработки; бинарные файлы располагаются в закрытом bucket. Клиент получает короткоживущие подписанные URL либо поток через авторизованный endpoint.

## Мобильное приложение

### Хранение

Токены сессии хранятся в `expo-secure-store`. В AsyncStorage не размещаются access/refresh tokens.

Будущая SQLite-миграция добавляет:

- `messenger_rooms`;
- `messenger_messages`;
- `messenger_reactions`;
- `messenger_attachments`;
- `messenger_outbox`;
- `messenger_sync_state`;
- `messenger_profiles`.

SQLite является локальным представлением. Права, членство и окончательные серверные номера сообщений всегда определяет backend.

### Маршруты Expo Router

- `/messenger` — комнаты и непрочитанные сообщения;
- `/messenger/chat/[id]` — переписка;
- `/messenger/profile/[id]` — профиль;
- `/messenger/invites` — приглашения;
- `/messenger/scanner` — QR-сканер;
- `/messenger/admin` — административный раздел;
- `/messenger/admin/users` — пользователи и сессии;
- `/messenger/admin/roles` — роли и права;
- `/messenger/admin/chats` — комнаты и правила;
- `/messenger/admin/reports` — жалобы и модерация;
- `/invite/[token]` — принятие приглашения через deep link.

### Синхронизация

1. Экран сразу читает разрешённый локальный снимок SQLite.
2. REST-запрос получает изменения после сохранённого курсора.
3. Сервер возвращает сообщения, реакции, изменения комнат и отзыв доступа в одном упорядоченном потоке синхронизации.
4. WebSocket доставляет новые события после базовой синхронизации.
5. Исходящее сообщение получает UUID `client_message_id` до записи в outbox.
6. Сервер использует `(sender_id, client_message_id)` как ключ идемпотентности и возвращает постоянный `message_id`.
7. После разрыва соединения клиент сначала выполняет catch-up по курсору и только затем считает WebSocket актуальным.

## Push-уведомления

- Один пользователь может иметь несколько записей `devices` и Expo push-токенов.
- Push создаётся после фиксации сообщения в PostgreSQL, а не до неё.
- Payload содержит тип события, `room_id` и `message_id`; доступ повторно проверяется при открытии приложения.
- Текст сообщения на заблокированном экране по умолчанию не передаётся; пользователь позднее может включить предпросмотр.
- Expo receipts обрабатываются фоновым заданием, а недействительные токены деактивируются.
- Текущие уведомления матчей и локальные уведомления тренировок сохраняются как независимые категории.

## Развёртывание и эксплуатация

- Отдельные `staging` и `production` окружения, БД и buckets.
- Секреты передаются через окружение/secret store и никогда не коммитятся.
- Миграции БД запускаются отдельной контролируемой командой перед обновлением API.
- Health endpoints разделяют готовность API, PostgreSQL, Redis и media worker.
- Структурированные логи содержат request/user/room IDs, но не текст сообщений, токены или подписанные URL.
- PostgreSQL и media bucket резервируются независимо; восстановление регулярно проверяется на чистом окружении.

## Серверный репозиторий на Этапе 1

Минимальная структура:

```text
apps/api/                 REST и WebSocket
apps/worker/              push и обработка медиа
packages/contracts/       OpenAPI, DTO и события
packages/rbac/            разрешения и policy engine
database/migrations/      миграции PostgreSQL
deploy/                   Docker Compose и Nginx
docs/                     эксплуатация и восстановление
```

Клиентские TypeScript-типы генерируются из `packages/contracts`, чтобы сервер и приложение не расходились по формату.
