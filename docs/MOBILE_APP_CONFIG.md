# MobileAppConfig.txt: полный механизм

`MobileAppConfig.txt` формируется WordPress-файлом `admin-startup-config.php` в формате `{ "status": "success", "data": { ... } }`. Клиент хранит последнюю корректную копию и стартовый экземпляр в SQLite, поэтому обычная ошибка сети не блокирует запуск.

## Последовательность холодного запуска

1. Клиент читает валидный локальный конфиг и сразу применяет его. При первой установке используется экземпляр из SQLite.
2. Применяются `api.base_url`, общий таймаут запросов и feature flags.
3. После первого интерактивного кадра клиент загружает свежий файл без HTTP-кэша. Новая ревизия применяется в этом же сеансе.
4. Диспетчер выбирает ровно одно состояние в порядке: технические работы → обязательное обновление → необязательное обновление → объявление.
5. Сворачивание и возврат в приложение не считаются запуском. Новый процесс приложения считается новым холодным запуском.

## Версии приложения и обновление

`app.latest_version` и `app.minimum_supported_version` задаются отдельно для `ios` и `android`. Сравнение выполняется по числовым частям (`2.4` равно `2.4.0`; суффикс сборки не влияет).

| Условие | Поведение |
|---|---|
| установленная версия ≥ `latest_version` | окно не показывается |
| `minimum_supported_version` ≤ установленная версия < `latest_version` | рекомендация с кнопками «Обновить» и «При следующем запуске» |
| установленная версия < `minimum_supported_version` | блокирующий экран без возможности закрыть |

Необязательное предложение можно пропустить до следующего холодного запуска; оно не записывается как навсегда просмотренное. Для iPhone открывается `app_store_url`. Для Android сначала используется прямая `android_download_url` на APK, а если она пуста — `google_play_url`. Обязательное окно остаётся поверх приложения после открытия ссылки.

Сначала нужно опубликовать сборку и проверить ссылку, затем выставлять `latest_version`. `minimum_supported_version` повышают только когда старый API-контракт действительно больше нельзя поддерживать.

## Технические работы

`maintenance.enabled=true` перекрывает весь интерфейс независимо от версии. Показывается `maintenance.message`. Повторная проверка доступна через `retry_after_seconds` (минимум 30 секунд), загружает свежий файл и автоматически снимает экран после отключения режима в админке.

## Объявления

Объявление показывается при `announcement.enabled=true`, заполненном `announcement.id` и отсутствии более приоритетного экрана. Заголовок, текст и необязательная ссылка берутся из `title`, `message`, `url`. После закрытия ID сохраняется на устройстве. Новый ID показывает новое объявление всем пользователям.

## Feature flags

| Поле | Что выключает при `false` |
|---|---|
| `features.push_notifications` | стартовую сверку серверной PUSH-подписки и локальный флаг PUSH |
| `features.live_scores` | периодический запрос счёта на открытой странице матча |
| `features.f2f` | вкладку и загрузку очных встреч на странице матча |
| `features.mobile_games` | пункт «Игры»; каталог показывает недоступность при прямом переходе |
| `features.home_games` | переключаемый блок текущих и трёх последних игр на главной |
| `features.home_news` | новостной блок на главной; новости продолжают открываться по прямой ссылке |

Неизвестные флаги игнорируются. Отсутствующий известный флаг считается включённым для совместимости.

## Главная страница и новости

Верхний блок главной страницы переключается между текущими играми и тремя последними завершёнными матчами, где домашняя или гостевая команда имеет ID `74` («Динамо-Форвард»). Ссылка «Смотреть все игры» открывает отдельный полный список матчей команды. Плитки старого быстрого меню, «Настройки» и «О программе» с главной удалены: эти маршруты доступны через постоянное нижнее меню.

Новости получаются штатным WordPress REST API: список — `/wp-json/wp/v2/posts` с ограниченным набором полей, полная запись — `/wp-json/wp/v2/posts/{id}`. Отдельный серверный PHP-эндпоинт не требуется. Главная сначала загружает три публикации; кнопка «Ещё» добавляет следующие три до последней страницы WordPress.

Каждая полученная порция накопительно записывается в SQLite-таблицу `news_articles` по WordPress ID. Индекс статьи (дата, заголовок, анонс, ссылка и главное изображение) и уже загруженное полное содержимое хранятся между запусками приложения. Перед повторной загрузкой полной новости клиент запрашивает только её поле `modified`: если ревизия не изменилась, сохранённый HTML и медиаданные используются без повторного скачивания. При изменении `modified` полное содержимое заменяется свежей версией. Индекс списка проверяется в фоне не чаще одного раза в десять минут; новые страницы, открытые кнопкой «Ещё», дописываются в ту же таблицу и не удаляют ранее сохранённые новости.

Полная новость отображает серверный `content.rendered`, поэтому WordPress/SportPress заранее разворачивает шорткоды. Турнирные таблицы не пересобираются клиентом: приложение сохраняет исходные строки, логотипы и выделение команды, добавляя адаптивные стили и горизонтальную прокрутку на узком экране.

Карусели FooGallery также берутся из развёрнутого HTML. Так как WordPress-плагин помещает реальные адреса фотографий в `data-src-fg`, клиент переносит их в `src` и оформляет элементы как горизонтальную карусель со snap-прокруткой. Это преобразование выполняется только при открытии конкретной новости. Изображения имеют `loading="lazy"`, поэтому начинают загружаться в фоне уже внутри страницы новости; на главной фотографии галереи не запрашиваются. В SQLite сохраняются HTML и URL, а не бинарные копии фотографий.

## API, данные и синхронизация

- `api.base_url` переключает WordPress REST API. В production принимается только HTTPS; завершающие `/` удаляются.
- `api.request_timeout_seconds` задаёт общий HTTP-таймаут и следующие проверки стартового файла; для файла диапазон ограничен 3–120 секундами.
- `data_versions.*` и плоские `*_version` независимо обновляют команды, игроков, арены, лиги, сезоны и турниры.
- `league_id`, `season_id`, `tournamentsNow`, `tournamentsPast` задают каталог турниров.
- `sync.historical_start_date`, `historical_delay_days`, `event_chunk_days` управляют пополнением архива матчей.
- `config_revision` увеличивается при сохранении и помогает диагностике. `config_schema_version` повышается только при несовместимом изменении структуры.

## Публикация и проверка

1. Сделать резервную копию PHP-файла и установить обновлённый `admin-startup-config.php`.
2. В WordPress открыть «Старт. конфигурация», заполнить версии и ссылки, сохранить.
3. Открыть `MobileAppConfig.txt`: проверить `status: success`, `config_schema_version: 2`, новую `config_revision` и корректный JSON.
4. Проверить на iOS и Android три диапазона версий, обе ссылки и закрытие мягкого окна только до нового холодного запуска.
5. По очереди проверить maintenance, объявление с новым ID и каждый feature flag. В конце вернуть рабочие значения и сохранить конфиг.

Нельзя тестировать объявление под включённым maintenance или обязательным обновлением: более приоритетный экран намеренно его скроет.
