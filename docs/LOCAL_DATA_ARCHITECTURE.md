# Локальная база данных и синхронизация

## Назначение

Приложение открывается на чистом устройстве без интернета и сразу содержит:

- команды, арены, игроков, лиги и сезоны;
- доступные логотипы команд;
- доступные фотографии игроков;
- 948 исторических игр за 2023–2026 годы;
- турнирные таблицы и их привязки к лигам и сезонам;
- версии наборов данных и курсор пополнения архива.

SQLite является основным источником справочников и истории. `AsyncStorage` сохранён только для совместимости, небольших пользовательских настроек и кэша сетевых экранов.

## Комплект поставки

`npm postinstall` подготавливает базу и манифест изображений:

- `assets/database/forward_seed.db` из `assets/database/seed-parts/`;
- `assets/player-photos/generated.ts` с явными `require(...)` для файлов из `assets/player-photos/source/`.
- `assets/logo/generated.ts` с явными `require(...)` для файлов `assets/logo/team_<ID>.*`.

Манифест базы содержит размер и SHA-256. В EAS-сборку попадает цельная база, а фотографии включаются Metro напрямую. При первом запуске база копируется в изменяемое хранилище приложения; встроенные фото не упаковываются, не распаковываются и не копируются приложением.

Команды: `npm run seed:generate`, `npm run seed:verify`, `npm run photos:generate`,
`npm run logos:generate`. Для получения актуальных логотипов из `/get-team`
используется `npm run logos:sync`; эта сетевая команда не запускается во время EAS-сборки.

## Схема и миграции

Текущая схема — v5, миграции последовательно применяются по `PRAGMA user_version`.

- `metadata(key PRIMARY KEY, value)` — конфигурация, даты seed и курсор архива.
- `sync_versions(entity PRIMARY KEY, version, synced_at)` — локальные версии наборов.
- `teams`, `venues`, `players`, `leagues`, `seasons` — справочники с `raw_json`.
- `events` — матчи, счёт, протокол, статистика и полный `raw_json`.
- `event_teams`, `event_venues`, `event_leagues`, `event_seasons` — индексируемые связи.
- `tournament_configs` — нормализованные строки таблиц, `league_id`, `season_id`, версия и время генерации.
- `trainings` — занятия типов лед/ОФП/игра, локальное время с зоной, команда, место, примечание и полный `raw_json`.

`database/repository.ts` — единственная точка чтения и транзакционной записи SQLite. Обновление справочника сначала получает и проверяет полный ответ API, затем заменяет набор и фиксирует его версию в одной транзакции. Исторические ссылки на удалённые команды сохраняются.

## Правила источников данных

| Данные | Основной источник | Условие сетевого обновления |
|---|---|---|
| Команды, арены, лиги, сезоны | SQLite | Соответствующая версия в конфигурации отличается от локальной |
| Логотипы команд | Встроенные assets + локальный fallback | Новая команда без встроенного asset загружается по `logo_url` |
| Игроки и фото | SQLite + локальные файлы | `players_version` отличается от локальной |
| Игры до 2026-08-01 | Только SQLite | Не запрашиваются повторно |
| Завершённые игры с 2026-08-01 | SQLite после фоновой синхронизации | Инкрементально до безопасной даты |
| Текущие и предстоящие игры | Последний снимок + API | Снимок открывает интерфейс; API обновляет его при каждом запуске и pull-to-refresh |
| Турнирные таблицы | SQLite | Только при отсутствии таблицы или изменении `tournaments_version` |
| Расписание тренировок | SQLite + API | SQLite открывает экран; API атомарно обновляет целые недели от предыдущей до 12 недель вперёд при запуске и pull-to-refresh |

Старый `MobileAppConfig.txt` содержал только `teams_version`. Пока новый PHP-файл не установлен, эта версия используется как совместная для команд, арен, лиг и сезонов. При первом сохранении новой конфигурации отдельные версии наследуют текущее значение `teams_version`, а не начинают с 1.

## Турнирные таблицы SportPress

Приложение не воспроизводит формулы SportPress. Сервер рассчитывает `[team_standings]` в полном WordPress и сохраняет готовый JSON. Standalone-обработчик отдаёт его без загрузки WordPress; при истечении TTL или изменении версии один запрос выполняет новый расчёт.

При запуске приложение сравнивает `tournaments_version` с `sync_versions.tournaments` и проверяет наличие каждой таблицы из стартовой конфигурации. Если всё актуально, сетевые запросы полностью пропускаются. Если версия изменилась, обновляются только устаревшие записи; общая версия фиксируется после успешной загрузки всего обязательного набора. Старый AsyncStorage-кэш однократно переносится в SQLite.

## Инкрементальный архив матчей

1. Начальная граница — `2026-08-01`.
2. Безопасная конечная дата — текущая дата минус `historical_delay_days` (по умолчанию 7).
3. Первый запрос идёт с начальной границы; успешные завершённые матчи сохраняются через UPSERT.
4. После успешной обработки каждой порции записывается `historical_events_through`.
5. Следующий запуск начинается с сохранённой даты минус один день. Перекрытие позволяет получить исправленный результат последнего дня.
6. Порции ограничены `event_chunk_days` (по умолчанию 180), поэтому большой отставший архив не создаёт один тяжёлый запрос.
7. При сетевой или серверной ошибке курсор не двигается.

Разделение запроса выполняется в `data/gameData.ts`: локальная часть читается из SQLite, часть после курсора — из API, затем результаты объединяются по ID. Поэтому архив, сезоны, команды и F2F используют одну логику.

## Быстрый запуск и сетевое обновление

Стартовая конфигурация хранится в локальном кэше и в metadata встроенной SQLite-базы. Если сеть не вернула новый `MobileAppConfig.txt` за 750 мс, инициализация использует локальную конфигурацию, а запрос продолжает выполняться в фоне. При отсутствии локальной копии первый запуск ожидает сетевой ответ только как аварийный сценарий: штатная сборка всегда содержит seed-конфигурацию.

Последний успешный результат мастер-запроса предстоящих игр хранится отдельным снимком `@offline/upcoming-master/v1`. Это важно, потому что ключ обычного кэша содержит `date_from` и меняется каждый день. При запуске снимок восстанавливается до сетевого запроса; пустой сохранённый массив является корректным набором данных. Через 750 мс splash-screen снимается даже при продолжающемся запросе. Когда API отвечает, подписчики экранов получают свежий список автоматически.

Фоновые ошибки и 12-секундный timeout остаются видны в диагностических логах, но не означают ошибку запуска. Сообщение «Нет подключения к интернету» на главном экране зависит только от подтверждённого состояния NetInfo, а не от медленного ответа, HTTP-ошибки или нулевого количества матчей.

## Локальный F2F

F2F запрашивает в SQLite матчи, в которых одновременно есть обе команды, исключает текущую игру и сортирует историю по убыванию даты. Старые матчи не требуют сети. Если диапазон запроса затрагивает ещё не архивированный свежий период, добавляется сетевой результат этой части.

## Тренировки и локальные напоминания

`services/trainingService.ts` сначала читает `trainings`, затем в фоне вызывает `/get-trainings`. При HTTP/системной ошибке записи не удаляются. После успешной валидации весь запрошенный диапазон заменяется транзакционно, поэтому удалённые на сайте занятия исчезают с устройства, а данные вне окна сохраняются.

Миграция v5 пересоздаёт таблицу `trainings` с допустимыми типами `ice`, `ofp` и
`game`, сохраняя уже загруженные строки. Это необходимо, поскольку ограничение
`CHECK` в SQLite нельзя расширить через обычный `ALTER COLUMN`.

Настройки напоминаний хранятся в AsyncStorage, а сами системные задачи создаёт `services/trainingNotificationService.ts`. При изменении расписания или выбранного интервала отменяются только ранее сохранённые идентификаторы тренировок и планируются ближайшие 60 будущих уведомлений. Время события приходит с ISO-смещением `Europe/Moscow`, поэтому момент срабатывания остаётся корректным и при другой зоне устройства.

## Фотографии игроков

В сборку входят файлы, вручную помещённые в `assets/player-photos/source/`. Имя имеет вид `player_<ID>.<extension>`, а `source/version.txt` должно совпадать с `players_version`. Генератор создаёт статическую карту `ID → require(asset)`. Если версия игроков не изменилась, приложение не вызывает `/get-players-full` и не проверяет каждую фотографию по сети.

При изменении `players_version` приложение:

1. получает новый полный список игроков;
2. скачивает фотографии непосредственно по `photo_url`, используя компактные варианты WordPress;
3. сохраняет их в локальный каталог по ID;
4. заменяет игроков в SQLite и фиксирует новую версию только после успеха.

При ошибке обновления предыдущий рабочий набор не удаляется. ZIP в мобильной сборке и в протоколе обновления не используется.

## Логотипы команд

Все изображения, доступные в `/get-team`, заранее сохраняются в `assets/logo/` под
именами `team_<ID>.<extension>`. Генератор создаёт статическую карту
`ID → require(asset)`, поэтому Metro включает файлы непосредственно в IPA/APK.
`loadTeamLogo()` сначала возвращает URI встроенного asset и не зависит от сети,
AsyncStorage или версии справочника команд.

Сохранённые карточки матчей при чтении повторно сопоставляют логотипы по ID, поэтому
пустой URI из старого кэша не переживает обновление приложения. Если после сборки
в API появляется новая команда, её логотип загружается в `documentDirectory` по
HTTPS и используется как локальный fallback до следующей синхронизации assets.

## Контракт пустого результата

`GET /get-events` должен возвращать HTTP `200`:

```json
{"status":"success","data":[],"count":0}
```

Пустой список — корректный результат, а не признак отсутствия интернета. Для обратной совместимости клиент также преобразует текущий HTTP `404` с `code: "no_results"` в пустой список.
