# ХК «Динамо Форвард 2014» — мобильное приложение

Мобильное приложение для просмотра матчей детской хоккейной команды, результатов, турнирных таблиц, состава игроков, архива игр и видеозаписей. Проект написан на React Native с Expo и Expo Router и выпускается для Android и iOS.

## Основной функционал

- Главный экран с текущими и ближайшими матчами.
- Просмотр списка предстоящих игр.
- Архив матчей по сезонам.
- Турниры, турнирные таблицы и статистика команд.
- Карточка матча: счёт, периоды, команды, арена и видео.
- Список игроков и персональные карточки.
- Страница команды и статистика игр.
- Push-уведомления о матчах через Expo Notifications.
- Расписание тренировок (лед, ОФП и игры), доступное из SQLite без сети.
- Индивидуальные локальные напоминания о тренировках за 15 минут — 3 часа.
- Аналитика AppMetrica.
- Мини-игры Memory и «Заливка льда»; экспериментальный аэрохоккей сохранён в проекте.
- Локальное хранение игроков, фотографий, команд, логотипов, турниров и матчей.

## Работа без интернета

Приложение использует SQLite как основной источник стабильных данных и API только для изменяемой части:

1. При наличии сохранённых данных интерфейс открывается сразу из локального хранилища.
2. При доступной сети данные обновляются в фоне.
3. Успешный ответ API атомарно заменяет соответствующий локальный кэш.
4. При сетевой ошибке последний успешный набор не удаляется.
5. При подтверждённом NetInfo отсутствии интернета пользователь видит одно неблокирующее уведомление внутри safe area главного экрана.
6. Пустой успешный ответ API, включая `count: 0` или `data: []`, означает «матчей нет» и не показывает сетевую ошибку.

При запуске приложение сначала читает встроенную или последнюю сохранённую конфигурацию. Сетевому обновлению `MobileAppConfig.txt` даётся 750 мс: быстрый ответ применяется сразу, а при более долгом ответе запуск продолжается с локальной копией. Запрос не отменяется и сохраняет новую конфигурацию в фоне. Если в фоне пришла другая ревизия, уведомление о версии приложения обрабатывается сразу, а новые версии наборов данных полностью применяются при следующем запуске.

После получения рабочей конфигурации приложение сверяет локальные версии справочников. Если данные полны и версии актуальны, последний успешный снимок текущих и предстоящих матчей восстанавливается сразу, а запрос свежих матчей запускается параллельно с локальной подготовкой игроков, фотографий и фоновых задач. Сетевому запросу также даётся 750 мс до снятия splash-screen. Более долгий запрос продолжает работу в фоне; после его завершения главный экран и экран всех матчей получают новый снимок автоматически. Если справочники требуют обновления, запрос матчей начинается после их обновления, чтобы не сохранить игры со старыми названиями, аренами или логотипами.

Предзагрузка игр текущего турнира выполняется только после завершения основного фонового запроса предстоящих матчей. Это исключает два одновременных тяжёлых обращения к `/get-events`. Тайм-аут API по-прежнему защищает фоновые задачи, но больше не удерживает стартовый экран на 12–16 секунд. Временное подробное логирование `[Инициализация]`, `[Предстоящие игры]`, `[Главный экран]` и `[Экран матчей]` показывает источник данных, длительность этапа и момент автоматического обновления интерфейса.

Постоянно сохраняются:

- стартовая конфигурация и версии данных;
- текущие и прошедшие турниры;
- команды и локальные логотипы;
- игроки и локальные фотографии;
- списки матчей отдельно для каждого набора фильтров;
- отдельный последний успешный снимок текущих и предстоящих матчей;
- расписание тренировок и время его последней успешной синхронизации;
- открытые карточки матчей;
- справочники лиг, сезонов и арен.

Первый запуск на полностью чистом устройстве возможен без интернета. В сборку включены SQLite seed-база с командами, аренами, игроками, лигами, сезонами, 948 историческими играми и 9 турнирными таблицами, а также архив доступных фотографий игроков. Текущие и предстоящие матчи, видео и сетевые функции без интернета недоступны, но это не блокирует запуск и просмотр архива.

Исторические игры до 31 июля 2026 года читаются только из SQLite. Завершённые игры начиная с 1 августа 2026 года приложение дозагружает до даты «сегодня минус 7 дней», сохраняет в SQLite и запоминает подтверждённую дату синхронизации. Следующая синхронизация повторяет предыдущий день для безопасного захвата исправлений. Подробности находятся в [docs/LOCAL_DATA_ARCHITECTURE.md](docs/LOCAL_DATA_ARCHITECTURE.md).

## Источники данных

Основной сайт и API принадлежат владельцу приложения и могут дорабатываться совместно с клиентом.

- Базовый API: `https://www.hc-forward.com/wp-json/app/v1`.
- Стартовая конфигурация: `MobileAppConfig.txt` в теме WordPress.
- Матчи: `/get-events`.
- Команды: `/get-team` и связанные методы `apiService`.
- Игроки: `/get-players-full`.
- Турнирные таблицы: `/get-table/{id}`.
- Тренировки: `/get-trainings`.
- Push-подписки: `/push-subscription`.

Сетевые контракты и преобразование ответов сосредоточены в `services/` и `data/gameData.ts`. При изменении API необходимо сохранять обратную совместимость либо одновременно обновлять типы в `types/`.

Для списочного `/get-events` пустая выборка возвращает HTTP `200` и `{ "status": "success", "data": [], "count": 0 }`. Для обратной совместимости клиент также понимает прежний ответ HTTP `404` с `code: "no_results"`, преобразуя его в пустой список.

### Ускоренный endpoint матчей

7 августа 2026 года для `/wp-json/app/v1/get-events` внедрён отдельный серверный обработчик `forward-get-events-fast.php`. Внешний URL и формат ответа не изменились: правило в `.htaccess` направляет только этот маршрут в standalone-обработчик, который запускает WordPress в режиме `SHORTINIT`, выполняет выборки через `$wpdb` и пакетно подготавливает метаданные и термины. Прежний REST endpoint сохранён как быстрый вариант отката: для возврата к нему достаточно убрать соответствующее правило rewrite.

Признаки нового обработчика в ответе:

- `X-Forward-Endpoint: standalone-shortinit-v1`;
- `X-Forward-API-Total-Ms` — полное время серверной обработки;
- `Server-Timing` — отдельные времена запуска WordPress, SQL-запросов и подготовки результата.

Подтверждённые замеры после прогрева:

| Сценарий | Результат | Время клиента | Время сервера |
| --- | ---: | ---: | ---: |
| Предстоящие матчи, пустой результат | 0 матчей | 119–125 мс | 46–53 мс |
| Карточка одного матча | 1 матч | 129–130 мс | 46–51 мс |
| Историческая выборка | 78 матчей | 311–312 мс | 61–63 мс |
| F2F двух команд | 15 матчей | 166–170 мс | около 48 мс |

До перенаправления сам `/wp-json/` и прежний `/get-events` тратили примерно 1,8–2,1 секунды до первого байта, хотя SQL выполнялся за доли миллисекунды. После внедрения standalone endpoint загрузка предстоящих матчей при старте приложения сократилась с 3306 до 186 мс, дополнительное ожидание — с 3227 до 111 мс, а общее время готовности приложения — с 3993 до 589 мс. Значения являются контрольными замерами конкретного устройства и сервера, а не гарантированным SLA.

Успешная пустая выборка возвращает HTTP `200`, `status: "success"`, `data: []` и `count: 0`; она не считается сетевой ошибкой. Фильтры `event_id`, `date_from`, `date_to`, `league`, `season`, обычный фильтр команд и F2F сохранены совместимыми с приложением.

### Турнирные таблицы

`/get-table/{id}` получает лигу и сезон записи `sp_table`, выполняет шорткод SportPress `[team_standings]`, а затем нормализует сформированный HTML в JSON. Поэтому расчёт не переносится на `SHORTINIT` или прямой SQL: источником истины остаётся полностью загруженный SportPress.

Для ускорения внедрён двухуровневый механизм:

1. WordPress/SportPress рассчитывает таблицу и атомарно сохраняет материализованный JSON.
2. Standalone endpoint по прежнему URL отдаёт готовый файл без запуска WordPress.
3. TTL по умолчанию составляет 300 секунд; первый запрос после истечения TTL пересчитывает таблицу, последующие читают кэш.
4. Сохранение матча или таблицы SportPress увеличивает `tournaments_version` и инвалидирует старый JSON.
5. Приложение хранит конфигурации таблиц в SQLite и не обращается к API при неизменной версии. Отсутствующие или устаревшие таблицы обновляются с ограничением параллелизма.

Подтверждённые замеры рабочего endpoint для таблицы 5977 из 12 строк:

| Состояние | Время клиента | Время сервера | Источник |
| --- | ---: | ---: | --- |
| Пересчёт после истечения TTL | 2164,6 мс | 1724,5 мс | `regenerated` |
| Прогретый кэш, типичные запросы | 79,5–104,9 мс | 1,0–2,0 мс | `hit` |
| Прогретый кэш при сетевых выбросах | 243,8–309,8 мс | около 1 мс | `hit` |

В холодном запросе 1621,9 мс серверного времени занимает запуск WordPress, тогда как сам шорткод SportPress — 79,2 мс, а разбор результата — 9,0 мс. Поэтому материализованный кэш устраняет именно основной источник задержки. В режиме `hit` сервер ускоряется примерно в 860–1700 раз, а типичное клиентское время — примерно в 20 раз. Более долгие отдельные `hit`-запросы относятся к сети или установлению соединения: сервер в этих случаях всё равно формирует ответ примерно за 1 мс.

Серверные файлы, безопасный порядок установки и отката находятся в [server/wordpress/README-TABLE-CACHE-RU.md](server/wordpress/README-TABLE-CACHE-RU.md). На рабочем сайте rewrite активен; признак успешного обращения к кэшу — заголовки `X-Forward-Endpoint: standalone-table-cache-v1` и `X-Forward-Cache: hit`.

### Расписание тренировок

Расписание хранится в записях **The Events Calendar**, созданных версионируемым MU-плагином `server/wordpress/forward-training-schedule.php`. Плагин добавляет в WordPress страницу **Инструменты → Импорт тренировок**, принимает JSON или XML, проверяет права и nonce, а перед записью сверяет каждую дату с указанным днём недели. Если `year` не задан, берётся текущий год WordPress. Повторный импорт обновляет занятие по стабильному UID, а режим `replace_range` позволяет убрать в корзину исключённые из нового расписания занятия внутри явно заданного периода.

На странице импорта есть конструктор записи с календарём, типом «Лед»/«ОФП»/«Игра», наименованием, временем и примечанием. Он дополняет существующий JSON или создаёт новый набор с безопасным `replace_range: false`. Заголовок без явно заданного наименования совпадает с типом: `Лед`, `ОФП` либо `Игра`.

Для расписания с исходного изображения подготовлен файл [training-schedule-2026-08.json](server/wordpress/training-schedule-2026-08.json): год в нём намеренно не указан и в текущем 2026 году определяется автоматически. Подробная установка, формат XML и команда проверки API описаны в [README-TRAININGS-RU.md](server/wordpress/README-TRAININGS-RU.md).

Мобильное приложение запрашивает целые недели от предыдущей до 12 недель вперёд. Только полностью успешный ответ атомарно заменяет это окно в SQLite; пустой `data: []` является нормальным расписанием. При ошибке остаётся последний сохранённый набор. Экран «Тренировки» всегда сначала читает SQLite, поэтому открывается офлайн.

На главном экране «Тренировки» входят в общую компактную сетку меню с подзаголовком «Недельное расписание». Стрелки переключают предыдущую, текущую и будущие недели, а у каждого занятия под временем выводится рассчитанная продолжительность. Во время занятия карточка постепенно заполняется серым слева направо; завершённое занятие остаётся полностью затемнённым.

По умолчанию экран скрывает занятия, закончившиеся до начала сегодняшнего дня. Иконка часов справа в заголовке возвращает прошедшие занятия текущей недели; повторное нажатие снова скрывает их. Контурная иконка означает скрытый архив недели, заполненная на подсвеченном фоне — включённый показ.

Уведомления о тренировках являются локальными и не зависят от серверной push-подписки на матчи. Пользователь выбирает опережение 15, 30, 60, 120 или 180 минут. После успешной синхронизации приложение перепланирует до 60 ближайших напоминаний, хранит только собственные системные идентификаторы и не отменяет уведомления других типов. Нажатие на напоминание открывает экран расписания.

### Мини-игра «Заливка льда»

Вторая игра раздела «Мобильные игры» находится в `app/mobilegames/ice-resurfacing/`. Игрок управляет ледозаливочной машиной кнопками газа и поворота, очищает матовый заснеженный лёд, а после достижения требуемого покрытия возвращается через анимированные верхние ворота. Отпускание газа даёт плавное торможение, быстрый поворот вызывает боковой занос, а удар о борт выше безопасного порога завершает заезд.

Время и доля незалитой площади рассчитываются физическим движком независимо от частоты обновления React-интерфейса. Покрытие хранится в компактной сетке, а для отрисовки объединяется в один SVG Path. Спрайт машины расположен в `assets/games/ice-resurfacing/resurfacer.png` и статически подключён через `require`, поэтому входит в IPA/APK и не зависит от сети.

Все отладочные параметры собраны в `app/mobilegames/ice-resurfacing/gameConfig.ts`: максимальная скорость, разгон, торможение, скорость руля, сцепление, начало и сила заноса, порог аварии, геометрия кондиционера и допустимый остаток площади. Подробные логи включаются одним флагом `DEBUG_LOGS` в том же файле.

## Архитектура

```text
app/                       Экраны и маршруты Expo Router
components/                Переиспользуемые UI-компоненты
contexts/                  Глобальное состояние сети
data/                      Сборка доменных данных приложения
database/                  Схема SQLite, миграции и инициализация
services/                  API, загрузка файлов, кэш и аналитика
types/                     TypeScript-контракты
utils/                     Форматирование и вспомогательная логика
plugins/                   Expo config plugins
server/                    Версионируемые серверные файлы WordPress
assets/                    Иконки, изображения и звуки
docs/                      Baseline и сценарии ручной проверки
```

Ключевые модули:

- `app/_layout.tsx` — запуск приложения, восстановление данных и фоновые задачи.
- `database/index.ts` — подключение bundled seed-базы и применение миграций.
- `database/repository.ts` — единый SQLite repository для справочников, матчей и тренировок.
- `app/trainings.tsx` — локальный-first экран расписания льда и ОФП.
- `services/trainingService.ts` — API-синхронизация и атомарная замена окна расписания.
- `services/trainingNotificationService.ts` — настройки и локальное планирование напоминаний.
- `database/migrations.json` — единый источник схемы для приложения и seed-генератора.
- `assets/database/seed-parts/` и `seed-manifest.json` — версионируемые части стартового снимка.
- `assets/database/forward_seed.db` — автоматически восстановленная перед запуском/сборкой SQLite-база.
- `services/startupApi.ts` — стартовая конфигурация, timeout/retry и fallback.
- `services/referenceDataService.ts` — обновление только изменившихся версионированных справочников.
- `services/historicalSync.ts` — инкрементальное пополнение завершённых матчей.
- `services/appUpdateService.ts` — рекомендуемое и обязательное обновление версии приложения.
- `services/persistentCache.ts` — типизированная оболочка постоянного кэша.
- `services/dataAvailability.ts` — состояние использования сохранённых данных.
- `contexts/NetworkStatusContext.tsx` — подписка на состояние сети.
- `app/index.tsx` — главный экран и единственное safe-area уведомление об отсутствии сети.
- `data/gameData.ts` — матчи, преобразование API и persistent SWR-кэш.
- `services/playerDataService.ts` — игроки, фотографии и атомарное обновление.
- `services/tournamentsApi.ts` — SQLite-кэш, нормализация и версионная синхронизация таблиц.
- `server/wordpress/` — генератор SportPress, standalone-выдача JSON и инструкция установки.
- `server/wordpress/forward-training-schedule.php` — импорт The Events Calendar и API тренировок.

## Локальная установка

Требования:

- Node.js не ниже `20.19`;
- npm;
- учётная запись Expo/EAS;
- для подписанных iOS-сборок — активная Apple Developer Program.

```bash
git switch stabilization/foundation
git pull --ff-only origin stabilization/foundation
npm ci
npm run check
```

Пересоздание и проверка seed-базы из текущего API:

```bash
npm run seed:generate
npm run seed:migrate
npm run seed:verify
```

Пересоздание встроенного архива фотографий игроков:

```bash
npm run photos:generate
```

Seed-база хранится в Git частями. Исходные фото хранятся в `assets/player-photos/source/`; `npm ci` автоматически генерирует явный Metro-манифест, и изображения напрямую попадают в приложение без ZIP.

По умолчанию загружаются матчи с `2023-01-01` по `2026-08-07`. Диапазон можно изменить:

```bash
npm run seed:generate -- --from 2023-01-01 --to 2026-08-07
```

Запуск Metro:

```bash
npx expo start
```

## EAS Build

`eas.json` содержит профили:

- `development` — development client;
- `preview` — APK и iOS Ad Hoc для физических устройств;
- `internal` — внутренняя сборка;
- `production` — App Store/Google Play.

EAS CLI не установлен в зависимостях проекта. Для воспроизводимой preview-сборки используется закреплённая версия 21.7.0:

```bash
npm run eas-build -- --platform android --profile preview
npm run eas-build -- --platform ios --profile preview
```

Для iOS Ad Hoc устройство предварительно регистрируется командой:

```bash
npx --yes eas-cli@21.7.0 device:create
```

## Секреты и конфигурация

- `google-services.json` не хранится в Git.
- Для Android EAS получает его через файловую переменную `GOOGLE_SERVICES_JSON` окружения `preview`.
- Apple и Android signing credentials хранятся на серверах Expo.
- Приватные ключи, `.p8`, `.p12`, keystore и provisioning profile исключены через `.gitignore`.
- Секретные значения нельзя добавлять в `app.config.js`, исходный код или README.

## Версионирование и ветки

- `main` — опубликованная/историческая линия приложения.
- `stabilization/foundation` — текущая стабилизация и реорганизация.
- Перед каждой сборкой выполняются `npm ci`, `npm run check` и smoke-тесты.
- `autoIncrement` в EAS увеличивает Android `versionCode` и iOS `buildNumber`.

## Известные ограничения

- Видеопотоки и внешние страницы требуют сети, даже если карточка матча доступна офлайн.
- Фоновая актуализация ограничена правилами iOS/Android; гарантированное обновление выполняется при активном приложении.
- Надёжность системных уведомлений проверяется в development/preview-сборке; Expo Go подходит для UI и локальных уведомлений, но не поддерживает всю нативную push-функциональность.
- Часть старых сервисов пока содержит совместимые legacy-методы; их удаление запланировано после стабилизации пользовательских сценариев.
